## Implemented capabilities

**Kernel (`@corestack/kernel`) — Release Candidate certified.** Zero
runtime dependencies, pure ES2022. Ports with in-memory reference
adapters: `EventBus`, `UnitOfWork`, `ProcessedEventStore` (idempotent
consumers), `Cache`, `RateLimiter`, `Encrypter`, `IdempotencyStore`
(request-key replay, `organizationId`-mandatory per ADR-0020),
`Clock`/`IdGenerator` (UUIDv7). `Context`/`Actor`/`DomainEvent` with
JSON-round-trippable envelopes. `Result`-based expected-failure handling;
a stable `CoreError` taxonomy.

**Platform (`@corestack/platform`) — 21 of 22 E03 tasks complete.**
Migration format + loader + runner (`platform.module_migrations`,
checksum drift detection, advisory-lock serialization); the full
transactional outbox (schema, writer, relay, crash-consistency suite,
partition maintenance); module lifecycle contract + `createCoreStack()`
composition; config validation (Zod, secret-ref indirection, aggregated
errors); health/readiness computation; graceful shutdown; the full
tenant-isolation stack (RLS harness, org-scoped repository base, context
resolution); the purge protocol; `PostgresUnitOfWork`; `PostgresRateLimiter`;
a `Cache` decision note (no Postgres backend, Redis deferred — ADR-0018);
`PostgresIdempotencyStore`.

**Tenant isolation — audited as one system and certified with residual
risks.** Every mechanism in
[tenant-isolation-certification.md](../security/tenant-isolation-certification.md)
is real, tested against actual PostgreSQL 18, and fails closed at every
empirically-checked boundary. One genuine cross-tenant vulnerability
(idempotency-key replay) was found and fixed during this pass, with
regression tests proven against the pre-fix code.

**Contributor tooling.** A mandatory ten-step tenant-safety guide, a
real golden-path example module (`examples/acme-crm-module`) built to
production rigor, and architecture-fitness rules (ADR-0021) enforcing
org-scoping and platform-table access discipline — extended to cover
`examples/*` too, catching a real layering violation the moment it was
turned on.

**Test coverage.** 375+ tests across kernel, platform (unit +
real-Postgres integration, never mocked), architecture fitness, and the
example module — every Postgres-backed claim in this codebase is proven
against a real database, either a local instance or Testcontainers.

## Known limitations

- **E03-T04 (migration authoring guide) was never built** — found during
  the E03 exit review, tracked as low-effort unscheduled debt, not
  blocking.
- **Operational tooling is documentation, not automation, in several
  places.** The outbox runbook's replay and admin-action procedures are
  manual SQL today.
- **Performance visibility is narrow.** A real benchmark baseline exists
  only for the outbox subsystem's six hot paths (single machine,
  unthresholded); every Postgres adapter added since (RLS, UnitOfWork,
  RateLimiter, IdempotencyStore) is proven _correct_ under concurrency but
  not benchmarked.
- **The observability contract is mostly aspirational.** Only relay lag
  is actually wired; logs/metrics vocabulary for the rest of the outbox
  subsystem is documented but not implemented.
- **Docker/Testcontainers is unavailable on the primary development
  machine used to build E03.** Every integration test has a local-Postgres
  fallback (`DATABASE_URL`), so this hasn't blocked verification, but
  E04-T02 (the Testcontainers harness task itself) will hit this directly.

## Infrastructure assumptions

- **PostgreSQL 18** verified directly; PostgreSQL 16 compatibility also
  verified empirically (`postgres-18-compatibility.md`) — the two behave
  identically for every mechanism this codebase depends on.
- **Node.js >= 20.11**, pnpm workspaces + Turborepo, ESM-only (ADR-0001).
- **No Redis, Kafka, RabbitMQ, or other infrastructure dependency is
  required** to run anything that exists in this repository today — the
  "Node + Postgres is enough" promise holds for every shipped component.
- Docker/Testcontainers is the intended CI verification path but is
  **not required for local development** — a local PostgreSQL instance
  via `DATABASE_URL` is a fully supported first-class mode, not a
  workaround.

## Contributor prerequisites

- A local PostgreSQL 18 (or 16+) instance for running integration tests,
  or Docker for the Testcontainers path.
- Read
  [docs/security/how-to-build-a-tenant-safe-feature.md](../security/how-to-build-a-tenant-safe-feature.md)
  and study `examples/acme-crm-module` before building anything that
  touches tenant-owned data — this is now the mandatory path, not a
  suggestion.
- Familiarity with this codebase's verification discipline: every claim
  about Postgres behavior is checked empirically before being coded
  against, and every new test is proven to fail against an intentionally
  unsafe implementation before being trusted.

## Security posture

**Certified with residual risks** (full verdict:
[tenant-isolation-certification.md §7](../security/tenant-isolation-certification.md)).
Zero open P0 findings repo-wide. The single highest-priority open item is
Residual Risk R3: no real deployment has ever connected as the restricted
RLS `app`/`platform` roles — the isolation mechanism is proven correct but
not yet proven _live_ in a real running system. See the
[security scorecard](../security/security-scorecard.md) for a
dimension-by-dimension breakdown (range: 5/10 operational visibility to
8/10 for data integrity, event safety, RLS enforcement, CI integrity, and
contributor safety).

## Upgrade expectations

Pre-1.0 semver per
[docs/engineering/09-release-versioning.md](../engineering/09-release-versioning.md):
**`0.x.y`, minor may break, patch never does**, every breaking minor
ships migration notes. No package in this repository has reached the M5
freeze review yet — nothing here has a stability guarantee beyond that
policy.

## Recommended audience for this alpha

**Internal engineering evaluation and architecture review — not
production SaaS deployment.** This alpha is appropriate for:

- Engineers evaluating whether CoreStack's Clean Architecture, tenant-
  isolation, and Postgres-first patterns fit a future project.
- Contributors building E04+ (testing infrastructure) or the first real
  feature modules on top of this foundation.

It is **not yet appropriate** for:

- Any production deployment handling real tenant data — Residual Risk R3
  (no real RLS role credentials) must be resolved first, and no
  authentication module (E06) exists yet to actually gate access to a
  real HTTP surface.
- Any workload requiring benchmarked, CI-gated performance guarantees —
  none exist outside the outbox subsystem's single-machine baseline.
